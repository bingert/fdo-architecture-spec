FDO Attribute Definitions

This section is normative.

[R-Attr-1] Attribute Definitions are FDOs

FDO attribute definitions (short: attribute definitions) are themselves FDOs. Hence, they are unambiguously identified by a PID that resolves into an FDO record consisting of attributes. An attribute definition defines the semantics and the value space of its instantiating attributes in all FDO records it is instantiated.

[R-Attr-2] Semantics of Attribute Definitions

Attribute definitions describe the semantics of an attribute using the 0.FDO/Name and 0.FDO/Description attributes. They MUST provide at least one localized and human-readable name for the attribute. For better understanding, at least one localized and human-readable description SHOULD be provided. Other information MAY be included in the attribute definition FDO records to refer to external resources and provide additional context for the semantics of the attribute.

[R-Attr-3] Cardinality of Attribute Definitions

An attribute definition MUST specify the cardinality of an attribute using the 0.FDO/Cardinality attribute. The cardinality defines how often this attribute is allowed to be instantiated in any FDO record. The cardinality MUST follow this regular expression: 
^(\d+)(\.\.(\d+|\*))?$
Examples for possible cardinalities include but are not limited to:
  • 1 (mandatory),
  • 0..1 (optional),
  • 1..* (mandatory and repeatable),
  • 0..* (optional and repeatable),
  • 2..3 (MUST occur two to three times).

[R-Attr-5] Attribute Validation Mechanisms

An attribute definition MAY specify validation rules on the value of any attributes instantiating the attribute definition. This specification defines five different attribute validation mechanisms that MAY be used to define such validation rules.

Each attribute validation mechanisms requires different attributes in its attribute definition record to denote those validation rules. Hence, each of these mechanisms uses its own FDO profile. If an attribute definition intends to use one of these mechanisms, it MUST indicate this by using the respective profile as the value of the 0.FDO/Profile attribute in its attribute definition record. The attribute validation mechanisms are:

  • Syntax, using the 0.FDO/AttributeDefSyntax profile (see ...)
  • Union, using the 0.FDO/AttributeDefUnion profile (see ...)
  • Inline Combination, using the 0.FDO/AttributeDefComb profile (see ...)
  • Profile Referencing, using the 0.FDO/AttributeDefProfileRef profile (see ...)
  • Attribute Referencing, using the 0.FDO/AttributeDefAttrRef profile (see ...)

[R5-13] Additional Attributes in Attribute Definition FDOs

Attribute Definitions MAY have additional attributes and instantiate additional profiles for any reason. This SHOULD be used to relate attribute definitions to existing external resources such as vocabularies, ontologies, or terminologies.

[R5-3] Attribute Categories

There are three qualitative categories of attributes (or attribute definitions): mandatory, optional, and community-defined attributes.
  • The FDO Forum defines a set of mandatory attributes that MUST be used in each FDO Record. This set is defined in the root profile.
  • The FDO Forum defines a set of optional, but recommended attributes. These include all attributes needed for the functioning of the FDO type system specified in this document (see ). It also includes some pre-defined attributes which SHOULD be reused by use-cases within their FDO Records and profiles (see ). Use-cases SHOULD reuse these attributes, whenever suitable, for better harmonization of FDO attribute information.
  • Community-defined attributes are any attributes that are defined by a community of practice (i.e., usually not the FDO Forum). Interoperability between different communities and their attributes can be facilitated by either reusing attributes with their semantic meaning in other communities, defining more generic attributes, or by providing a bidirectional mapping process. They appear in different forms, with decreasing level of machine-actionability in the following enumeration:
    • A community attribute MAY be specified as an attribute definition, according to – , against which the instantiated attribute in an FDO Record MUST be validated. The Attribute definition is instantiated as the following attribute:
      • first element: the PID or the name of the attribute definition
      • value: any literal that correctly validates against the first element
    • Community attributes MAY be used in records by referencing existing elements in vocabularies, terminologies, or ontologies. Validation MAY be performed, but is not guaranteed. See for more details. Such an attribute looks as follows:
      • first element: reference to an element from a vocabulary, terminology, or ontology
      • value: instantiates the first element
    • Community attributes MAY be used in records by a simple human-readable label. No validation can be performed here.
      • first element: human-readable label
      • value: any literal

    These levels do not impose additional requirements but help repositories and users to assess validation behavior, interoperability, and long-term interpretability of FDO Records.

[R5-14] FDO Forum Attribute Definitions

The attribute definitions listed in Tables 1–4 (comprising the mandatory and optional attributes defined by the FDO Forum) are implemented within the Data Type Registry (DTR) by the FDO Forum. Those attribute definitions are implemented as Handles and SHOULD be reused in any FDO implementation independent of the used technology. This ensures interoperability between different FDO implementations and compliance with the type system.
